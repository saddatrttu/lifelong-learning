## 为什么需要工作流

工作流 = **分支策略 + 合并规则 + 发布节奏** 的团队约定。统一工作流让团队：

- 减少冲突与踩坑
- PR/评审有统一规范
- 发布可预测、可回滚
- 新人能快速上手

> 工作流是**团队共识**，比"哪个最好"更重要。选一个大家都能遵守的。

---

## 集中式工作流

最简单：所有人都在 `main` 分支工作。

```
main ──●──●──●──●──●──
```

- 适合：极小型项目、个人仓库、一对多教学
- 优点：零学习成本
- 缺点：无隔离，冲突多，不适合多人并行

---

## GitHub Flow

轻量、以 PR 为中心，GitHub 官方推荐。

```
main ──●──────────●──────────●
        \          /          /
         ●─●─●    /          /    feature 分支
                  ●─●        /    hotfix
```

### 规则

1. `main` 永远**可发布**（随时处于可部署状态）
2. 新功能从 `main` 开 `feature/xxx` 分支
3. 提交要小而频繁，尽早 push
4. 随时开 PR（WIP 也行），触发 CI
5. PR 通过评审 + CI 后合并到 `main`
6. 合并即发布（配合自动部署）

### 适合

- 持续部署的 Web 应用
- 快速迭代、每周多次发布的团队
- 小到中型团队

## Git Flow

经典但较重的分支模型，适合**版本化发布**。

```
main ──●──────────────●── (v1.0) ────●── (v1.1)
        \            /                /
develop──●────●────●────●────●───────
        |    |    |         \
        |    ●    ●──(hotfix)  ●──(release)
feature─●    分支：feature/* 合并进 develop
```

### 核心分支

| 分支 | 用途 | 从哪来 | 合并到哪 |
|------|------|--------|---------|
| `main` | 正式发布 | — | — |
| `develop` | 开发主干（集成） | main | main（发版时） |
| `feature/*` | 功能开发 | develop | develop |
| `release/*` | 发布准备（修 bug） | develop | main + develop |
| `hotfix/*` | 紧急修复 | main | main + develop |

### 适合

- 需要维护多个发布版本的产品（桌面软件、移动 App）
- 版本化发布 + 打 tag（见 [[6-Git-高级技巧]] 的 tag）
- 较大的正式团队

> ⚠️ Git Flow 分支多、流程重，对快速迭代的团队可能过重。

## Trunk-Based 开发

所有开发者共享一条主干（trunk/main），分支存活期极短（<1 天）。

```
main ──●──●──●──●──●──●──●──●
            (小批量合并，配合特性开关)
```

### 规则

1. 直接（或极短生命周期分支）提交到 main
2. 依赖**特性开关（feature flags）**控制未完成功能
3. 持续集成，频繁合并，避免大 merge
4. 配合自动测试，保证 main 常绿

### 适合

- 大规模团队、Google/Facebook 风格
- 高发布频率
- 有成熟 CI 与特性开关体系的团队

## 选择工作流

| 工作流 | 复杂度 | 发布节奏 | 适合场景 |
|--------|--------|---------|---------|
| 集中式 | 低 | 随意 | 个人/小项目 |
| GitHub Flow | 中 | 频繁持续 | Web、SaaS、快速迭代 |
| Git Flow | 高 | 版本化 | 多版本产品、正式发布 |
| Trunk-Based | 中高 | 极快 | 大规模、特性开关成熟 |

> 💡 **起步建议**：团队从 GitHub Flow 开始最稳妥；有明确版本发布需求再升级到 Git Flow。

## CI/CD 集成

### CI（持续集成）：合并前自动验证

PR 触发流水线跑：lint → 单元测试 → 构建 → 安全检查。**绿了才能合并**。

```
git push → CI 运行 → 结果回写 PR → 通过才可合并
```

常见平台：GitHub Actions、GitLab CI、Jenkins。

### 保护分支（Protected Branches）

在 `main` 上强制：

- 要求 PR + 至少 1 个评审通过
- CI 必须通过
- 禁止直接 push / force push
- 保持分支最新（合并前 rebase）

### CD（持续部署）：合并后自动发布

- GitHub Flow：合并到 main → 自动部署到生产
- 回滚：`git revert` 新提交 → 自动重新部署

> 💡 AI 工具可辅助自动化 Git 流程（如 [[0-Claude Code 使用指南]] 中可通过 Hooks/子代理自动跑测试、提交、开 PR）。

## 团队约定清单

把下面这些写进仓库 `CONTRIBUTING.md` 或 `.github/`：

| 事项 | 约定示例 |
|------|---------|
| 分支命名 | `feature/xxx`、`fix/xxx`、`hotfix/xxx` |
| 提交规范 | Conventional Commits（见 [[2-Git-核心命令与提交]]） |
| PR 模板 | 改动、原因、测试方式、关联 issue |
| 评审标准 | 阻塞/建议/可选分级（见 [[4-Git-远程协作与PR]]） |
| 合并方式 | Squash merge（默认） |
| 测试要求 | CI 全绿才能合并 |
| 安全红线 | 禁止 force push main；密钥禁止入库 |
