## 稳定性第一

自动化测试的**最大敌人是 flaky（不稳定）**。一个"十次过九次"的测试没有任何价值——它只会消耗信任。

### flaky 常见来源

| 来源 | 对策 |
|------|------|
| 元素等待不足 | 显式等待期望状态，不 sleep（[[6-Test-Appium元素定位与交互]]） |
| 用例共享状态 | 每条用例独立数据（[[1-Test-测试方法论核心]]） |
| 依赖顺序 | 用例不依赖执行顺序 |
| 时间/网络波动 | 接口测试设置超时与重试；UI 用稳健等待 |
| 定位器脆弱 | 优先 ID/text，少用 XPATH 全路径 |
| 环境脏数据 | 独立测试账号、随机后缀数据 |

### 稳定性规则

1. **能确定的就别猜**：等待状态而非固定时间
2. **用例独立**：不共享可变数据
3. **失败可复现**：截图 + page_source + 日志三件套
4. **统计 flaky**：持续跟踪，看到 flaky 立即修
5. **慎用重试**：`--reruns` 只是掩盖，要修根因（见 [[superpowers-使用说明]] 的系统化调试）

## pytest 与 Appium 融合

用 **pytest 统一编排**单元、接口、Appium UI 测试，共享 fixture、配置、报告：

| 层次 | 工具 | 编排方式 |
|------|------|---------|
| 单元测试 | pytest | 普通用例 |
| 接口测试 | pytest + requests | 普通用例 + API 封装 |
| UI 测试 | pytest + Appium | Appium driver fixture + Page Object |

### 融合要点

1. **driver 是 fixture**（session/function 级），生命周期 pytest 管理
2. **Page Object** 封装 UI 细节，用例层与接口用例风格统一
3. **共享 conftest**：环境配置、日志、失败截图 hook
4. **统一报告**：Allure / pytest-html 一套出
5. **mark 分类**：`smoke` / `api` / `ui` / `slow`，CI 分套件跑

### 融合示例

```python
# tests/test_app_order.py
import pytest
from pages.login_page import LoginPage

@pytest.mark.smoke
def test_app_place_order(driver):
    home = LoginPage(driver).login("tester", "123456")
    order = home.place_order(item="咖啡")
    assert order.status == "待支付"
```

> 💡 融合的核心是**统一风格 + 共享基础设施**，而不是把代码搅在一起。接口层（api/）、页面层（pages/）、用例层（tests/）职责分离（[[7-Test-测试框架工程化]]）。

## 测试分层取舍

回归 [[1-Test-测试方法论核心]] 的金字塔，实践中的取舍：

| 场景 | 推荐 |
|------|------|
| 业务规则验证 | 接口测试（快、稳） |
| 模块逻辑 | 单元测试 |
| 端到端用户路径 | 少量 Appium UI 用例 |
| 界面视觉/复杂交互 | 少量 UI + 手动探索 |
| 高频回归 | 单元 + 接口为主 |

**决策口诀**：
- 能用接口测的**不用 UI 测**
- 能写单元测的**不上移**
- UI 层只留**关键路径 + 冒烟**
- 测试金字塔失衡时，先把底层补厚

## 团队落地清单

从"个人会写"到"团队规范"：

**基础设施**
- [ ] 统一目录结构（api/pages/tests/config/utils）
- [ ] 共享 conftest 与配置
- [ ] pytest.ini 统一规则与 mark

**规范**
- [ ] 用例命名规范（`test_行为_期望`）
- [ ] Page Object 覆盖所有被测页面
- [ ] 数据驱动：用例数据不入代码
- [ ] 提交前本地跑通相关套件

**CI**
- [ ] 单元 + 接口：每次提交自动跑
- [ ] UI 冒烟：合并/发布前跑
- [ ] 失败截图、报告、日志归档

**持续**
- [ ] 跟踪通过率 / flaky / 覆盖率指标
- [ ] 定期清理冗余与失效用例
- [ ] 与 [[0-Git 使用说明]] 的分支保护、评审流程配合

## 常见坑

| 坑 | 后果 | 对策 |
|----|------|------|
| 用例全堆 UI 层 | 天天红、维护成本爆炸 | 测试金字塔（[[1-Test-测试方法论核心]]） |
| 固定 sleep | flaky、跑得慢 | 显式等待期望状态 |
| XPATH 全路径定位 | UI 微调就全崩 | ID/text/content-desc |
| 用例共享数据 | 顺序依赖、互相污染 | 每用例独立数据 |
| 数据写死在代码里 | 改数据要改代码 | 参数化 + 数据文件 |
| 失败只重试 | 掩盖真 bug | 修根因 + 截图定位 |
| 大框架一上来就搭 | 学习成本高、没人用 | 分阶段演进（[[7-Test-测试框架工程化]]） |
| 只刷覆盖率数字 | 测试没测到点上 | 关注行为覆盖与关键路径 |

## 故障排查速查表

| 症状 | 排查 | 解法 |
|------|------|------|
| Appium 元素找不到 | 截图 + page_source | 等待/定位器/context（[[6-Test-Appium元素定位与交互]]） |
| 用例偶发失败 | 看是否 flaky | 独立数据 + 稳健等待 |
| driver 连不上 | `adb devices` / appium 日志 | 环境配置（[[5-Test-Appium基础]]） |
| 接口 500 | 服务端日志 vs 请求参数 | 接口层定位（[[4-Test-接口测试实践]]） |
| 中文乱码 | — | `unicodeKeyboard`+`resetKeyboard` |
| 用例间互相影响 | 数据/状态共享 | 独立 fixture 数据 |
| 报告没图 | 路径/权限 | 配置截图目录 + Allure |
| 覆盖率为 0 | 没装 pytest-cov | `--cov=src` |

## FAQ

**Q：pytest 和 Appium 是什么关系？**
A：pytest 是测试框架（组织、执行、断言、报告）；Appium 是移动端 UI 自动化引擎。两者配合：pytest 负责"怎么跑"，Appium 负责"怎么操作手机"。

**Q：单元测试、接口测试、UI 测试都要写吗？**
A：理想情况下都要，但**数量按金字塔分配**：单元最多、接口中等、UI 最少。资源有限时优先单元 + 接口。

**Q：Appium 能测 Web 页面吗？**
A：能。Appium 支持 Web 自动化（配合 Selenium 定位），也支持混合 App 的 WebView（见 [[6-Test-Appium元素定位与交互]]）。

**Q：iPhone 和 Android 能共用一套用例吗？**
A：框架层能共用（pytest + Page Object），但定位器因平台差异需分别封装（见 [[6-Test-Appium元素定位与交互]] 的多平台部分）。

**Q：Appium 比 Selenium 复杂，值得学吗？**
A：如果你的产品有移动端，值得。移动端元素定位、手势、WebView 混合、多设备都是 Selenium 覆盖不到的。

**Q：测试数据从哪来？**
A：接口造数（最快）、独立测试账号、随机后缀；避免依赖 UI 操作造数据（[[4-Test-接口测试实践]]）。

**Q：测试老红，团队没信心怎么办？**
A：先治 flaky（稳定性第一），再逐步提高通过率，用指标说服团队（[[1-Test-测试方法论核心]]）。

**Q：和 CI 怎么接？**
A：见 [[7-Test-测试框架工程化]] 的 CI/CD 部分：单元/接口每次提交，UI 冒烟合并前，配报告归档。
