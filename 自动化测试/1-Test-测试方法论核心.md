## 为什么需要测试

测试的价值不是"写代码验证"，而是：

- **回归保护**：改一处代码，不破坏其他功能
- **可验证的进度**：测试通过 = 功能真的完成（而非"看起来完成"）
- **重构的安全网**：有测试才敢重构，否则重构 = 重写
- **文档价值**：测试是"可执行的规格说明书"
- **尽早发现 bug**：发现越晚，修复成本越高

> 结合 [[superpowers-使用说明]] 的 TDD 理念：**测试先行**——先写失败测试，再写最小实现，最后重构（RED-GREEN-REFACTOR）。

## 测试金字塔

```
         ▲         UI 自动化测试
        / \        （Appium）——少而精
       /   \       慢、脆、维护成本最高
      /     \
     /       \     服务/接口测试
    /         \    （pytest + API）——中等
   /           \   快、稳、成本中等
  /_____________\
     单元测试         底层最多
    （pytest）       极快、成本最低、覆盖率核心
```

**为什么金字塔形**：
- 越底层越便宜：跑得快、维护少、定位准
- 越上层越昂贵：UI 依赖全部系统，任何一层坏了都挂
- 覆盖策略：底层多覆盖逻辑分支，上层只验证关键用户路径

**核心结论**：**80% 用例放底层（单元 + 接口），UI 层只留关键路径的端到端冒烟用例**。

## 测试分层策略

本套方法论的三层分工：

| 层 | 工具 | 验证什么 | 典型用例数 | 执行频率 |
|----|------|---------|-----------|---------|
| 单元层 | pytest | 函数、类、模块逻辑 | 最多 | 每次提交 |
| 接口层 | pytest + requests | API 契约、业务规则、鉴权 | 中等 | 每次提交 / CI |
| UI 层 | Appium | 端到端用户路径、跨组件交互 | 最少 | 主分支 / 发布前 |

**分层联动**：
- 接口逻辑错了 → 单元层先拦住
- 接口参数/响应错了 → 接口层拦住
- 前端交互断了 → UI 层拦住
- 每层拦住的问题越往下，修复成本越低

> 💡 **倒金字塔的陷阱**：如果团队大量用例堆在 Appium UI 层，会陷入"测试天天红、改不动、没人看"的恶性循环。UI 层要克制。

## 测试类型全景

| 类型 | 定义 | 用在本套体系哪里 |
|------|------|-----------------|
| 单元测试 | 隔离验证最小代码单元 | pytest（[[2-Test-pytest入门]]） |
| 接口测试 | 验证 API 输入输出契约 | pytest + requests（[[4-Test-接口测试实践]]） |
| 集成测试 | 多模块/多服务协作 | pytest 编排 |
| 端到端测试 | 完整用户路径 | Appium（[[5-Test-Appium基础]]） |
| 冒烟测试 | 核心功能快速过一遍 | 精简版 UI/接口用例 |
| 回归测试 | 改动后验证既有功能 | 全量自动化用例 |
| 性能测试 | 响应时间/吞吐 | pytest 可选（配合工具） |
| 兼容性测试 | 多设备/多版本 | Appium 多平台（[[6-Test-Appium元素定位与交互]]） |

## 用例设计原则

### 好用例的标准

1. **单一职责**：一个用例只验证一件事
2. **确定性**：结果不依赖运行顺序、时间、外部状态
3. **可读性**：断言清晰，"Given-When-Then" 结构
4. **可维护**：数据和逻辑分离，改需求只改数据
5. **快速**：单元用例毫秒级，接口秒级

### Given-When-Then 结构

```
def test_用户余额足够时可下单():
    # Given 前置条件
    setup_user_with_balance(100)

    # When 执行动作
    result = create_order(price=50)

    # Then 验证结果
    assert result["status"] == "success"
    assert result["balance"] == 50
```

### 边界与等价类

| 技术 | 说明 | 示例 |
|------|------|------|
| 等价类划分 | 同一行为的分组取一个代表 | 有效手机号 / 无效手机号 |
| 边界值分析 | 测边界最容易出错 | 0、1、99、100、负数 |
| 错误推测 | 凭经验猜易错点 | 空值、超长、特殊字符、并发 |

## 质量指标

| 指标 | 含义 | 注意 |
|------|------|------|
| 覆盖率 | 被测试代码行/分支占比 | 高覆盖率 ≠ 高质量，别为数字刷用例 |
| 通过率 | 通过的用例 / 总数 | 一直保持高位才有意义 |
| 稳定性 | 重跑结果一致 | 看 flaky（不稳定）用例数 |
| 维护成本 | 用例编写/修复耗时 | 越高说明设计越差 |
| 缺陷逃逸率 | 上线后被发现的 bug | 综合反映体系有效性 |

**指标工具**：pytest 的 `coverage` 插件（见 [[3-Test-pytest进阶]]），报告展示见 [[7-Test-测试框架工程化]]。

## 自动化 vs 手动

| 维度 | 自动化 | 手动 |
|------|--------|------|
| 适用 | 回归、重复、频繁、稳定 | 探索性、一次性、UI 视觉、复杂场景 |
| 成本 | 前期高、长期低 | 前期低、长期高 |
| 速度 | 快（可并行/夜间跑） | 慢 |
| 覆盖 | 程序化覆盖 | 人工直觉 |
| 脆性 | 易 flaky | 无 |

**选择原则**：
- 用例要**稳定**才值得自动化
- **探索性测试**永远需要人工
- 自动化 ≠ 取代手动，是释放人力去做探索性测试

## 方法论的落地

从"理论"到"团队日常"，按以下步骤落地：

```
1. 建测试金字塔意识 → 明确三层各自职责
2. 搭 pytest 基础框架（[[7-Test-测试框架工程化]]）
3. 从核心模块开始写单元测试（TDD，见 [[superpowers-使用说明]]）
4. 补关键 API 的接口测试（[[4-Test-接口测试实践]]）
5. 只给最关键用户路径做 Appium UI 用例（[[5-Test-Appium基础]]）
6. 接入 CI，让每次提交自动跑（[[7-Test-测试框架工程化]]）
7. 用指标持续优化：稳定性、通过率、覆盖率
```

**三步起步原则**（避免一口吃成胖子）：
- 第一步：核心业务单元测试跑通
- 第二步：核心 API 接口测试接入 CI
- 第三步：2-3 条关键 UI 路径的冒烟用例
- 稳定后再逐步扩展
